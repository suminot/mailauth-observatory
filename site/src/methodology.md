# 方法論

## 何を測っているか

DNS に公開されているレコードだけを見ています。SPF / DKIM / DMARC と、
MTA-STS / TLS-RPT / BIMI / DNSSEC / DANE です。メールの内容も配送も
見ていません。**標準への準拠状況の計測であり、各社のセキュリティを
総合評価するものではありません。**

## 8つの工程

| 工程 | 内容 |
|---|---|
| P1 母集団確定 | 一次名簿から上場企業を確定する（**母集団ごとに名簿が違う** ── 下記） |
| P2 ドメイン候補生成 | 公式サイト、CT ログ、SPF の `redirect=` / `include:`、DMARC の `rua=`、手動辞書から候補を広げる |
| P3 メールドメイン確定 | 候補を絞り、確度（confirmed / likely / unknown / parked）を付ける |
| P4 DNS計測 | レコードを取得し、応答をそのまま保存する |
| P5 パース | 保存した応答を仕様に照らして解釈する |
| P6 推察 | 辞書と照合してメール基盤や製品を推定する |
| P7 集計 | 公開用の統計を作り、前月との差分を計算する |
| P8 公開 | このサイトを生成する |

各工程は独立して実行でき、何件処理して何件失敗したかを必ず記録しています。

### 母集団ごとの一次名簿

| 母集団 | 一次名簿 | 補う情報 |
|---|---|---|
| 国内上場企業 | 金融庁 EDINET コードリスト | 国税庁 法人番号（商号・所在地）、gBizINFO（公式サイト） |
| 米国上場企業 | SEC EDGAR（パブリックドメイン） | Wikidata（公式サイト。SEC の website 欄はほぼ空） |

**EDINET は国内の名簿なので、米国の母集団には使っていません。**
業種も同じで、国内は EDINET の33業種、米国は SEC の SIC を、それぞれ
ISIC Rev.4 を経由して共通12分類に写しています。

出典表記はページ下部に出ますが、**公開している母集団に応じて変わります。**

## 「取れなかった」と「無かった」を分けている

DNS の応答が SERVFAIL や タイムアウトだった場合、それは「レコードが無い」
ことの証明にはなりません。この2つを別の事実として扱っています。

- 率の分母には**観測できたドメインだけ**を使う
- 前月あったドメインが今月観測できなかった場合、「消滅」とは数えない。
  消滅と判定するのは2回続けて観測できて不在だった場合のみ

## 起点ドメインが取れなかった企業

計測は各社の公式サイトのドメインを起点にして、そこから候補ドメインを広げて
いきます。**公式サイトが分からない企業は、候補ドメインが1件も作られません。**

このような企業は率の分母に入っていません。総括の「企業 N 社」は母集団の
社数であって、**そのすべてを測れたという意味ではありません。** 差がある月は
その社数を数字の横に出しています。

公式サイトは、法人番号を鍵にして政府の法人情報（gBizINFO）と Wikidata から
引いています。どちらにも無い企業が残ります。**推測で埋めることはしません** ──
別の会社のドメインを測ってしまう方が、測れないことよりも重い間違いだからです。

## 計測対象から外した分がある

計測対象から外すと決めたドメインには、以降 DNS の問い合わせを行いません。**「除外した」は「観測できなかった」
でも「レコードが無かった」でもなく、「測らないと決めた」という第三の状態です。**

除外した件数は各月の実行記録に残しています。**黙って分母から外すと、率が
理由の説明できない形で動き、読み手には計測失敗と区別が付かないため**です。

## 事実と推察を分けている

DNS から直接読み取れる値と、辞書との照合による推定は別のものとして扱い、
このサイトでも視覚的に分けています。推定には必ず確度と根拠が付きます。

## メール基盤をどう推し量っているか

「このドメインは Microsoft 365 を使っているらしい」という推定は、
**DNS に出る4種類の痕跡を辞書の正規表現と照合して**出しています。
Microsoft 365 の場合はこうです。

| 痕跡 | 見ているもの | 例 |
|---|---|---|
| MX | 受信を受け付けるホスト名 | `<名前>.mail.protection.outlook.com` |
| SPF の `include:` | 送信を許可している相手 | `spf.protection.outlook.com` |
| DKIM の CNAME | 署名鍵の置き場所 | `<selector>._domainkey` → `*.onmicrosoft.com` |
| 所有権確認 TXT | 登録時に置く確認用の値 | `MS=ms########` |

**どれも「契約している」という記録ではありません。** DNS にそう書いてある、
というだけです。

### 痕跡には強さの差があります

強い順に **DKIM の CNAME ≧ MX > SPF の `include:` > 所有権確認 TXT** として
扱っています。

- **DKIM の CNAME が一番強い。** 署名鍵の置き場所は、実際にそこで
  署名していないと意味を持ちません
- **MX は受信を指しますが、前段の製品が握っていることがあります。**
  その場合 MX から見えるのは前段だけで、後ろの基盤は見えません
- **`include:` は送信を許可しているだけ**で、常用しているとは限りません
- **所有権確認 TXT が一番弱い。** 登録したまま解約しても消し忘れられます。
  これしか根拠が無い場合は確度を `low` にし、対応する MX / SPF / DKIM の
  裏付けがあるかを別に記録しています

痕跡が2種類以上そろうと確度を1段上げます。DKIM の CNAME があれば `high`
にします。

### 前段と実基盤を別々に出しています

MX を握る製品（受信の前段）があると、MX だけ見て「その会社の基盤は前段の
製品だ」と読めてしまいます。**それは後ろにある実基盤を消してしまいます。**

そこで3つの層に分けて、それぞれ別に数えています。

| 層 | 何か |
|---|---|
| 実基盤 | メールボックスがある場所 |
| 受信の前段 | MX を握っている製品。この後ろに実基盤がある |
| 送信の前段 | MX を握らず、送信だけを通す製品 |

**同じ企業が3つの層すべてに出ることがあります。** 受信と送信で別の会社を
使っている例を実際に観測しています。同じ層の中では1ドメインにつき1つだけ
数えます（複数の痕跡があるときは強い方を採ります。両方数えると合計が
100%を超えるためです）。

売っている会社と中身を作っている会社が違う製品（OEM）は、**売っている会社
ごとに行を分けたうえで、`OEM元` を併記**しています。1つに丸めると
「どの会社の顧客か」が消え、分けたままにすると「中身は同じ仕組み」が
見えなくなるためです。

### 分からなかった理由を分けています

「基盤が分からない」には種類があり、混ぜると読み違いになります。

| 理由 | 中身 |
|---|---|
| API 連携型 | 配送経路に入らない製品。**原理的に DNS に出ません** |
| MX が自社ドメイン配下 | 運用はしています。製品名が見えないだけです |
| SPF が展開済み | `include:` を IP に展開してあり、相手の名前が残っていません |
| テナント用の仮 MX | 登録はされていますが、受信はそこではありません |
| 観測できなかった | 引けませんでした。「無い」ではありません |

**いずれも「使っていない」ではありません。** 利用率の分子にも分母にも
入れていません。

### 辞書について

照合に使う辞書は設定ファイルとして持っており、**その版を計測結果と一緒に
記録**しています。後から「この数字はどの辞書で出したか」を辿れます。

辞書に無い MX ホストは、件数の多い順に作業リストとして毎月出しています。
**辞書は必ず遅れます** ── 遅れている範囲が見えるようにしてあります。

企業数が5社未満のベンダーは「その他」に束ねています。件数は残しています。

## どのドメインを測っているか

計測の起点は各社の**登記ドメイン**（`example.co.jp` のような eTLD+1）です。
そこから候補を広げます。

| 経路 | 中身 |
|---|---|
| 公式サイト | 政府の法人情報と Wikidata から引いた公式 URL |
| CT ログ | 証明書の透明性ログに出ている名前 |
| SPF の `redirect=` | SPF を別ドメインに委ねている先 |
| SPF の `include:` | 自社サブドメインに分割している先 |
| DMARC の `rua=` | レポートの宛先が自社ドメインの場合 |
| 証明書の組織名 | **起点が取れなかった企業だけ。** 証明書の組織名で証明書ログを引く |
| 手動辞書 | グループ会社・事業ブランドを人手で足す経路 |

### 起点が取れなかった企業について

計測は各社の公式サイトのドメインを起点にしますが、**公式サイトが分からない
企業があります。** その企業はここまでの経路では候補が1件も作られません。

**メールを使っていないわけではありません。** ドメインを見つけられていない
だけです。

そこで、起点が取れなかった企業に限り、**証明書の組織名**から引いています。
サーバ証明書のうち企業実在確認を伴うもの（OV / EV）は、発行元の認証局が
登記を確認して組織名の欄を埋めます。**そこから引くのは推測ではありません。**
国内企業の英字社名は EDINET のコードリストから取っています。

**ただし、この検索は似た名前の別会社も返します。** 実測では
`Toyota Motor Corporation` で引いた1万件のうち 6,721 件が
`Toyota Motor Credit Corporation`（別会社）でした。**組織名が完全に一致する
証明書だけ**を採り、`Inc.` や `Corporation` といった法人格の語も落としません
── 落とすと別会社との区別が付きにくくなる方向にしか働かないためです。

<div class="limits">

- **無料の証明書には組織名の欄がありません。** そうした証明書だけを使って
  いる企業は、この経路では見つかりません。**見つからないことは、メールを
  使っていないことを意味しません**
- 証明書ログの検索には1回あたりの件数上限があります。同名・類似名の会社に
  押し出されて一致が0件になった場合は、**「無かった」ではなく「確かめられ
  なかった」として記録**しています

</div>

### 会社のメールがサブドメインにあることがあります

登記ドメインでメールをしていない会社があります。`_dmarc.example.co.jp` の
レポート宛先が `mail.example.co.jp` を指していて、**そちらが自分の MX と
自分の DMARC を持っている**という形です。この場合、登記ドメインだけを見て
出した数字は、その会社の実際のメールについて何も言っていません。

そこで、**メールの痕跡から出てきたサブドメイン**（`rua=` の宛先、SPF の
`redirect=` / `include:`、手動辞書）は捨てずに残し、そのうち
**自分の MX か自分の `_dmarc` を持っていたものだけ**を計測しています。
証明書ログに出るだけの名前（配信や検証用のもの）は、MX も `_dmarc` も
無いので自然に落ちます。

- **サブドメインは他のどの割合の分母にも入れていません。** 混ぜると
  ドメイン数が増え、前月と比べられなくなるためです。別枠で数えています
- **見つかった分だけです。** サブドメインの全数を DNS から列挙する方法は
  ありません。ここに出ないことは「無い」を意味しません
- 見つける経路は上の3つに限っています。それ以外の経路でメールを出している
  サブドメインは見えません

### `p=` と `sp=` は別のものです

DMARC の `p=` はそのドメイン自身に効きます。**配下のサブドメインに効くのは
`sp=` で、書かれていなければ `p=` を継承します。**

`p=reject; sp=none` と書かれている場合、そのドメイン自身には `reject` が、
配下には `none` が適用されます。両方を別に数えています。

**ただし、サブドメインが自分の `_dmarc` を持っている場合は `sp=` を継承
しません。** その場合 `sp=` の数字はそのサブドメインの実態を表しません。

計測したサブドメインについては、**自分の `_dmarc` が無ければ上位の `sp=` を
継承したものとして数えて**います。継承かどうかは区別して出しています。

<div class="limits">

- **直近の上位しか見ていません。** `a.b.example.co.jp` の `b.example.co.jp`
  に別の設定があっても、そこを計測していなければ見えません
- 継承元を計測できていない場合は、**継承していないもの**として扱います。
  「上位が無い」のではなく「上位を見ていない」です

</div>

## 検出できないもの

### API 連携型のメールセキュリティ製品

MX を変更せず API や OAuth で連携する製品は、原理的に DNS に痕跡を残しません。
**検出されなかったことは、使っていないことを意味しません。**

### DKIM のセレクタ

DKIM のセレクタは DNS 上で列挙できません。既知のセレクタ辞書で照会しており、
辞書に無いセレクタを使っている場合は検出できません。「既知セレクタでは
検出できなかった」と「設定していない」は別の状態として記録しています。

### MTA-STS のモード

`enforce` か `testing` かは DNS からは分かりません。ポリシーファイルを
HTTPS で取得する必要があり、現時点では取得していません。

### 転送経路

DMARC の効果は転送やメーリングリストの経路に左右されますが、DNS の観測からは
分かりません。

## DMARC の実効強度を二通りに計算している

RFC 7489 は `pct` を尊重し、RFC 9989（DMARCbis）は `pct` を扱わず `t=y` で
テスト扱いに落とします。どちらの解釈でも同じ結果になるとは限らないため、
両方を計算して保存しています。

## Organizational Domain の解決も二通り

Public Suffix List による解決と、RFC 9989 の Tree Walk による解決の両方を
計算しています。`.co.jp` 系や多階層のサブドメインで差が出ることがあります。

## 再現できるようにしている

取得した DNS の応答は加工せずに保存しており、解釈にバグが見つかった場合は
保存した応答から作り直します。集計に使った辞書の版も出力に記録しています。
計測のコードと設定は、計測結果と同じ版で保管しています。
